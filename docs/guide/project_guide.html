The brief and the answers

The dataset came without questions, so the brief was set first: three questions an airline network team would ask.

QuestionWhat it asksAnswer
1. Network & route performanceWhich routes and airports drive revenue; which underperform on load factor and fare?Pune is the hub (31% of revenue). 45 of 179 routes make 80%. 53 star routes earn 40%; 48 routes trail on both LF and RASK (19%).
2. Demand trendsHow are passengers, load factor and revenue moving, 2025 vs 2024?Jan-May: passengers +25%, revenue +71%. Fares +39% from Nov 2024; LF +1.9 pp.
3. KPI designOne KPI linking capacity to revenueRASK = revenue per available seat-km: ₹0.176 in 2025, +15%, on target.
Why set a brief? Without one, a dashboard becomes a chart gallery. Three explicit questions decide every page, measure and visual that follows.

The distance problem. 86% of flights carry their true great-circle distance, so the field is real. The other 14% carry another route's distance: PNQ-BOM recorded as 1,138 km is the Delhi-Mumbai distance; the true figure is 124 km.
Why it matters. RASK divides revenue by seat-km. With wrong kilometres, every per-km number for the Mumbai and Pune routes would be wrong.

The two rules, in plain words

  1. Distance: keep the recorded km when it is within 0.9-1.25× the great-circle distance; otherwise use the great-circle km.
  2. Fare outlier: flag a flight whose fare per passenger is above 3× its route's median. A per-km test was tried first and rejected: short routes naturally earn more per km, so it flagged every Pune-Mumbai flight.
GreatCircle = 6371 * 2 * Number.Asin(Number.Sqrt(
    Number.Power(Number.Sin((d_lat - o_lat) * r / 2), 2)
  + Number.Cos(o_lat * r) * Number.Cos(d_lat * r) * Number.Power(Number.Sin((d_lon - o_lon) * r / 2), 2)))
Distance Km = if not (ratio >= 0.9 and ratio <= 1.25) then Number.Round(GreatCircle) else [Distance]
No rows removed. 930 flights share a flight number, date and route with another flight but have different seats, passengers and revenue: they are separate operations.

Data model

A star schema written as TMDL by _build/make_semantic_model.py, then opened in Power BI Desktop.

  • Role-playing airports: the same reference list loads twice, as Origin and Destination, each with a one-to-many link.
  • Date table ends on the last flight (31 May 2025), so 2025 vs 2024 compares Jan-May with Jan-May.
  • Auto date/time off: no hidden date tables.
  • Forecast tables read the notebooks' CSVs; a shared Scenario table lets one slicer drive both.
Why write TMDL instead of clicking? The model is generated from one script, so it can be rebuilt, reviewed in Git and reused for the next project.

Lessons learned

What to carry into the next project.

  1. Check the denominator first. A per-km KPI is only as good as its kilometres; geography caught a silent lookup error.
  2. Compare like with like. Short routes earn more per km; outliers must be judged within their route.
  3. Benchmarks must ignore the visual's own filter. Use REMOVEFILTERS on the dimension, not ALLSELECTED.
  4. Price can move without volume falling. Fares rose 39% and load factor still rose: test elasticity before assuming it.
  5. Generate, don't click. Model, pages, notebooks, visuals and this guide are scripts, so the next project starts from them.
  6. Change model queries with Desktop closed; measures can be changed live; pages go in through Apply external changes.
  7. Say what the data can't support. Load factor tops out at 66.7% and fares average ₹293: comparisons hold, rupees are illustrative.
